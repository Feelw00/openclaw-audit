# PROOF — CAND-032 (pre, e2e)

**status**: `unreproducible`
**scenario**: `proof-CAND-032-e2e`

unit-level proof (PROOF-CAND-032-pre-20260514-100639.md) 의 후속 production e2e 검증.
unit-level 은 backend.queueMessage 를 직접 stub 으로 throw 시켜 5/5 unhandled 수집했으나,
production env (telegram channel + 실 openclaw bundle + mock LLM) 에서는 3 attempt 모두
reply-run-registry path 자체가 활성화되지 않음.

## 진단

CAND-032 의 결함 path:
```
queueReplyRunMessage (reply-run-registry.ts:496-507)
  if !operation || phase != "running" || !backend.queueMessage → false
  if !backend.isStreaming() → false
  void backend.queueMessage(text)  ← .catch 부재
```

queueReplyRunMessage 의 단일 caller (pi-embedded-runner/runs.ts:197-198):
```
const handle = ACTIVE_EMBEDDED_RUNS.get(sessionId);
if (!handle) {
  const queuedReplyRunMessage = queueReplyRunMessage(sessionId, text);
  ...
}
```

즉 reply-run path 진입 조건: **ACTIVE_EMBEDDED_RUNS.get(sessionId) 가 undefined** + reply-run-registry
의 operation 가 phase=running + backend.isStreaming() true 인 상태.

production e2e 에서:
- 첫 메시지로 reply-run start → attempt.ts:2828 `setActiveEmbeddedRun(sessionId, ...)` 가
  ACTIVE_EMBEDDED_RUNS.set
- 두 번째 메시지가 도착하면 ACTIVE_EMBEDDED_RUNS 에 sessionId 존재 → handle path 로 진입
  (queueReplyRunMessage 호출 안 함)
- ACTIVE_EMBEDDED_RUNS 가 cleanup (runs.ts:525-526 / 548) 되는 시점은 run end. 그러나 run end
  시점에 reply-run-registry 의 operation 도 함께 cleanup 되는 것으로 보임.

3 attempt 의 LLM stream 강제 abort 도 ACTIVE_EMBEDDED_RUNS 정리 + 자동 retry 패턴으로
귀결됨. retry 도중 ACTIVE_EMBEDDED_RUNS 는 sessionId 유지. 두 lifecycle 사이 좁은
window 가 production e2e 에서 자연스럽게 노출되지 않음.
