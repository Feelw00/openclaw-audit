## 결함 재요약

authGroups Map 을 iterate 하면서 각 group 의 queue 를 drain 하는 도중 `clearSessionQueues`
trigger 가 발사되면 일부 group (예: Y group) 의 fire 가 누락 또는 중복 처리 가능.

`drain.ts:89` 의 `resolveFollowupAuthorizationKey` 가 authGroup key 를 구성할 때 보는 필드:
- `senderId`
- `senderE164`
- `senderIsOwner`
- `execOverrides`
- `bashElevated`

## e2e 검증이 불가능한 이유

**authGroups ≥ 2 trigger 조건이 single telegram user account 로는 만들 수 없음**:

- single telegram user account 가 보내는 모든 메시지는 위 sender 필드가 **모두 동일**
  → authGroups Map 에 1 entry 만 등록 → inner-for race window 자체가 안 열림.
- `execOverrides` / `bashElevated` 도 audit-side 에서 메시지별로 다르게 설정할 production
  진입 path 가 없음 (collect-mode drain 의 production entry 가 그걸 노출 안 함).

### 필요한 인프라 (실현하지 않음)

burner phone 으로 **2nd telegram user account** 추가 set-up 시에만 e2e 가능:
1. burner phone 실 구입 + telegram 가입 + Telethon API key
2. 두 account 가 같은 group/chat 에 동시 메시지 보내는 driver
3. clearSessionQueues trigger 와 race window 측정 sideband

대안으로 시도한 것들 (전부 production-faithful 위반):
- single account 로 두 different sender field 시뮬: production code path 우회 필요 (감사 가치 0)
- execOverrides 직접 inject: production entry path 없음
- bashElevated 토글: 메시지별 변화 path 부재

## drop 사유 (2026-05-15 사용자 결정)

production reproducibility 인프라 부담 큼 + effective severity 추정 낮음:

- **인프라 부담**: 2nd telegram account set-up (burner phone 비용 + 2nd Telethon driver
  + 2-account coordination logic) — multi-session size.
- **effective severity 낮음**: authGroups ≥ 2 가 production 에서 발생하려면 같은 채널/세션에
  multi-user 또는 user + bot 동시 메시지 + race window (drain 도중 clearSessionQueues).
  자연 발현 빈도 낮음. unit-level proof 도 race window 좁아서 측정 difficulty 보고됨.
- **CAL-003 위험**: CAND-032 (reply-run-registry race window 좁음으로 e2e unreproducible)
  와 유사한 종류 — unit-level reproducibility 강해도 production hot-path 발현 가능성 낮은
  결함은 SOL/PR 가치 의문. CAL-003 의 "synthetic-only" warning 적용 후보.

unit-level callCount/queue 측정은 결함 메커니즘 입증이지만 production hot-path 자연
발현 가능성 낮음 + 인프라 비용 크다고 판단. **CAND-033 자체 drop**.
