## production sequence 분석

self-recurse 가 발동되는 production-faithful trigger 좁음:

| trigger 후보 | 위치 | production-faithfulness | 발동 빈도 |
|---|---|---|---|
| `runWithModelFallback` throw (LLM error) | followup-runner.ts:260-354 | n/a | **inner catch (358-363) 가 잡고 return → drain self-recurse 발동 안 함** |
| `resolveQueuedReplyExecutionConfig` throw | followup-runner.ts:201 | invalid plugin path 또는 gateway error 시. synthetic 위험 | drain catch 까지 propagate |
| `runPreflightCompactionIfNeeded` throw | followup-runner.ts:241 | session totalTokens 임계치 + compactEmbeddedPiSession 의 모든 model fallback 실패 시 | 동일 propagate |
| `sendFollowupPayloads` throw | followup-runner.ts:465 | routeReply 안의 unhandled throw (bot token revoke, chat removed 등) | 동일 propagate |
| `createReplyOperation` throw | followup-runner.ts:214 | rare | 동일 propagate |

**핵심 제약**: LLM throw (`runWithModelFallback`) 는 followup-runner.ts:358 의 inner catch
가 잡아서 `return undefined` 처리 → drain.ts 의 outer catch+finally 까지 propagate **안 함**.
즉 mock LLM throw 만으로는 self-recurse 발동 불가능.

추가 제약: self-recurse path 진입 조건은 **enqueue-followup activation** (agent-runner.ts:1185-1197).
이건 first message 처리 중에 second message 가 도착해야 하는 timing path.

## e2e cost 분석

production-faithful trigger 후보 3가지 평가:

### 옵션 A: `resolveQueuedReplyExecutionConfig` throw (invalid plugin path)

- 셋업: isolated config 의 secret target 에 존재 안 하는 plugin path 등록
- 위험: cli 부팅 단계에서 fail 가능성 (사전 dry-run 필요). synthetic trigger 이므로
  cross-review reproduction-realist 가 CAL-003 으로 reject 가능
- 추정 cost: 1-2시간

### 옵션 B: `runPreflightCompactionIfNeeded` throw (compaction 단계)

- 셋업: isolated home 의 sqlite session store 에 totalTokens=1M 사전 삽입 + mock LLM 의
  compaction 호출만 5xx (다른 호출은 success)
- 위험: session sqlite schema 학습 필요. preflight trigger 자연 활성화 위해 session
  totalTokens 가 정확한 threshold 초과해야 함
- 장점: production code path 가장 자연스러움 (cross_review_decision 의 caveat 가 권위로
  지목한 trigger source — contextEngine.compact())
- 추정 cost: 3-5시간

### 옵션 C: `sendFollowupPayloads` throw (routeReply unhandled)

- 셋업: 첫 메시지 성공 + 둘째 메시지 enqueue → followup turn 의 reply 전송에서 routeReply
  내부 unhandled throw 유도
- 위험: routeReply 의 throw 경로는 catch 로 잡히는 경우 많음 (followup-runner.ts:150-167
  의 `if (!result.ok)` 분기). production throw 유발 매우 어려움
- 추정 cost: 4-6시간 + 미발현 가능성

## 결정

**`abandoned` — CAND-031 drop**. SOL 작성 진입도 안 함.

근거:
1. **production reproducibility 매우 어려움**. self-recurse trigger 는 LLM throw 가 아닌
   LLM 외부 throw (config / preflight / routeReply) 뿐인데, 이건 모두 비정상 환경
   (invalid plugin / gateway error / fs corruption) 에서만 발동. 정상 production 운영의
   hot-path 가 아님.
2. **trigger window 매우 좁음**. enqueue-followup activation 자체가 first+second message
   의 좁은 timing path. self-recurse 발동 trigger 가 그 timing window 안에 동시 충족해야 함.
   CAND-032 와 동일 종류 reproducibility risk.
3. **effective severity 낮음**. drain.ts:303-313 코드 로직 자체는 결함 (max-attempts 부재)
   이지만, production 자연 trigger 가 비정상 환경 한정이라 실 영향 범위 좁음. P3 severity
   가 cross-review 에서 이미 medium pushback 받은 점도 반영.
4. **SOL 작성 가치 의문**. 메인테이너에게 reject 또는 closed-by-no-action 위험 큼 — fix 의
   real-world 효용 demonstrate 어려움. CAL-001 (메인테이너 reject) + CAL-008 (잔여
   reliability burden 만 추가) 의 hybrid 위험.
