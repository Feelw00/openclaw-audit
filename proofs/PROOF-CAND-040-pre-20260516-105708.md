## 옵션 C trial-and-error — silent skip 원인 정밀 식별 (이 세션)

직전 세션 (2026-05-15) blocked: stub 의 `availability.isConfigured` 호출 0회. 4 후보 (channelConfigs / capabilities / 누락 adapter / origin) trial-and-error 권고됐었음. 이번 세션은 trial 대신 **silent skip path 코드 추적** 으로 정확한 root cause 발견:

### 1차 발견 — register store 분리

`approval-handler-bootstrap.ts:49-52` `resolveChannelApprovalCapability(plugin)` 첫 가드 + L161 `watchChannelRuntimeContexts({channelRuntime: params.channelRuntime, ...})` watcher + L189 `getChannelRuntimeContext({channelRuntime: params.channelRuntime, ...})` 모두 caller (`server-channels.ts:494`) 가 넘긴 `channelRuntimeForTask` 의 store 에서 lookup.

`channelRuntimeForTask` = `createTaskScopedChannelRuntime({channelRuntime: await getChannelRuntime(channelId)}).channelRuntime` — server-side store wrap. `getChannelRuntime` (`server.impl.ts:164-169`) = cached `createRuntimeChannel()` instance.

stub README 의 "lease.jsonl readback_self 가능" 는 stub 의 plugin-loader-side `api.runtime.channel.runtimeContexts` 의 self-loop 만 증명 — server-side store 일치 보장 0. plugin loader 가 자체 `createPluginRuntime()` (loader.ts:1621) 호출 시 매번 별개 `createRuntimeChannel()` instance. stub 의 register store ≠ caller lookup store → silent skip.

### 2차 발견 — register 시점 vs 위치

`extensions/telegram/src/monitor.ts:163-170, 215-222` pattern: telegram 은 `register(api)` 가 아니라 **`startAccount` 안에서 `opts.channelRuntime` (caller 가 넘긴 server-side store) 사용해 `registerChannelRuntimeContext` 호출**. 이게 server-side store 와 자동 일치하는 production mechanism.

### 3차 발견 — native adapter 부재로 deliveryPlan.targets=[]

stub 수정 후 1차 재시도: `availability.isConfigured` ✅ `shouldHandle` ✅ `buildPendingPayload` ✅, 하지만 `prepareTarget` 호출 0. `approval-native-delivery.ts:42-56`: `if (!adapter) return {targets: []}` — `capability.native` 없으면 plan 이 empty.

`createChannelApprovalHandlerFromCapability` (approval-handler-runtime.ts:465) 가 `nativeAdapter: params.capability?.native as ChannelApprovalNativeAdapter | null` 사용. 우리 stub 은 `nativeRuntime` 만 있고 `native` 없었음 → empty plan → prepareTarget skip.

### 4차 발견 — prepareTarget 반환에 dedupeKey 필요

`approval-native-runtime.ts:96` `deliveredKeys.has(preparedTarget.dedupeKey)`. 부재 시 `undefined` 가 dedupe key 가 되어 같은 request 의 다음 target 이 skip 됨. minimal `dedupeKey: "audit-stub:{requestId}:{surface}"` 추가.

### 5차 발견 — server-side lease dispose trigger 부재

scenario 의 `dispose-lease.release` flag 는 stub 의 plugin-loader-side lease 만 dispose 시켰음. server-side store 의 lease (startAccount 안에서 등록) 는 별도 trigger 필요. stub 의 startAccount 안에 file-flag watcher 추가 → flag fire 시 server-side lease.dispose() → emitRuntimeContextEvent("unregistered") → approval-handler-bootstrap.ts:179 stopHandler → handler.stop → adapter.onStopped → `activeEntries.clear()` (approval-handler-runtime.ts:656-672).

### 6차 — probe ack 대기 제거

gateway exec.approval.request 의 ack 는 deliverPending 완료 후 회신. stub 의 deliverPending 가 park 중이면 ack 안 옴. probe 가 ack 대기하면 race window trigger 못 함. probe 수정: `exec.approval.request.sent` 후 즉시 calls.jsonl polling 으로 deliverPending.enter 관측 + race trigger.
