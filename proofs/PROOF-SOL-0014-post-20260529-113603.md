## 왜 이전 접근들이 with/without delta 를 못 냈나 (그리고 v2 가 어떻게 내나)

1. **proof-CAND-045 (truncate 모델)** — probe 가 `writeFileSync(authPath, truncated)` 로 authPath 를 직접
   truncate. fix(temp+rename)는 authPath 를 직접 안 건드리므로 raw/atomic 양쪽 동일 lockout → 구분 불가
   (`blocked-env`).

2. **proof-CAND-045-realproc-v2 watch-kill 모드 (real SIGKILL)** — 자식 node 가 단일 `set()` 로 큰 payload 를
   persist 하는 동안 부모가 write 진행을 감지해 즉시 SIGKILL. 실측 결과 macOS/APFS 에서 한 번의
   `writeFileSync(buffer)` 는 **단일 write() syscall** 이고, 커널이 page cache 로 전량 복사를 마친 뒤에야
   비동기 시그널을 처리하므로 SIGKILL 이 그 write 를 못 가른다(64MB payload 5회 SIGKILL → on-disk authPath
   가 full 67,108,925 bytes / parseOk=true → corrupt=0). payload 를 키워도 단일 syscall 이라 동일. v1 의
   freeze=0/100 과 같은 근본 원인. **SIGKILL ≠ 이 결함의 재현 수단** 임을 실측으로 확정.

3. **proof-CAND-045-realproc-v2 ulimit 모드 (채택)** — 자식에 `RLIMIT_FSIZE` 를 부과하면 커널이 write()
   syscall 자체를 한도 경계에서 끊는다. payload(8MB) > limit(2MB) 이면 write 가 2MB 까지 디스크에 남고 나머지는
   `EFBIG` 로 실패한다. 이것은 **디스크가 가득 차거나(ENOSPC) 쿼터(EDQUOT)에 걸리거나 파일 크기 한도(EFBIG)에서
   write 가 중간에 실패하는 실제 프로덕션 실패 클래스** 의 직접 재현이며, on-disk 바이트 상태는 "write 도중 전원
   차단으로 잘린 파일" 과 동일하다.

   결정적으로, `persistProviderChange`(`auth-storage.ts:286-305`)는 write 에러를 `try/catch` 로 **삼켜**
   `recordError` 만 하고 rethrow 하지 않는다. 따라서:
   - raw: `writeFileSync(authPath, 8MB)` → authPath 가 2MB partial 로 잘림. set() 은 성공한 척 리턴 →
     다음 런치 `reload()` 의 `JSON.parse(partial)` throw → `loadError` → 모든 `getApiKey` undefined →
     게다가 `persistProviderChange` 의 `if (loadError) return`(`:287`)이 재로그인 write 도 막아 **영구 lockout**.
   - atomic: `replaceFileAtomicSync` 가 sibling temp(`auth.json.<pid>.<uuid>.tmp`, flag `wx`)에만 write →
     동일 EFBIG 가 temp 에서 발화하고 `finally` 가 그 temp 를 정리. authPath 는 한 번도 write 대상이 된 적
     없으므로 직전 valid seed 그대로 → lockout 미발현 (구조적 0).

## 정직한 한계 (PR body `What was not tested` 로 forward)

- 중단 메커니즘은 `RLIMIT_FSIZE`(파일 크기 한도)이며 literal SIGKILL/전원차단이 아니다. 이유: macOS/APFS 에서
  버퍼 문자열의 단일 `writeFileSync` 는 한 번의 write() syscall 이라 비동기 SIGKILL 이 그것을 못 가른다(위 watch-kill
  실측). 파일 크기 한도는 write() 를 커널 경계에서 끊어 디스크에 진짜 partial 을 남기고, 그 바이트 상태는
  power-loss 로 잘린 파일과 동일하며 disk-full(ENOSPC)/quota(EDQUOT)/EFBIG 라는 실제 프로덕션 실패와 직접 대응한다.
- 진짜 power-loss(page cache 소실)는 별도 재현하지 않았다.
- OAuth refresh 경로(`withLockAsync`, `:164`)는 동일 write+동일 fix 를 공유하나 별도 실행 안 함(등록된 OAuth
  provider 필요).
- macOS/APFS 한정. rename 원자성 보장은 POSIX 레벨이며 타 플랫폼 별도 재검증 안 함.
