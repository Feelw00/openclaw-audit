## 문제 요약

`src/tasks/task-registry.ts` 의 두 mutator 가 동일한 ordering+보호 결함을 공유한다. in-memory `tasks` / `taskDeliveryStates` Map(및 owner/parentFlow/relatedSession/runId 인덱스)을 먼저 mutate-commit 한 뒤 sqlite persist 를 호출하고, 그 persist 호출을 try/catch/rollback 으로 감싸지 않는다 — `deleteTaskRecordById`(2162-2163 in-memory delete → 2165-2166 persist), `updateTask`(997 `tasks.set(taskId, next)` → 1011 `persistTaskUpsert`, 그 다음 try(1012)는 `syncFlowFromTask` 만 감쌈). default store 는 항상 트랜잭션 변형(`upsertTaskWithDeliveryState`/`deleteTaskWithDeliveryState`)으로 바인딩되어 production persist 는 무조건 `withWriteTransaction(BEGIN IMMEDIATE)` 를 경유하고, 이는 SQLITE_BUSY(다중-writer busy_timeout 5s 초과)/SQLITE_FULL(disk-full)/SQLITE_IOERR 시 ROLLBACK 후 error 를 re-throw 한다(store.sqlite.ts:503-506). persist 호출을 감싸는 try/catch 가 없으므로 throw 가 그대로 전파되고 in-memory mutation 은 되돌려지지 않아 in-memory(새 상태)와 sqlite(이전 상태)가 발산한다. FIND-001(P1, lost-delete): reload(`reloadTaskRegistryFromStore`, run-loop.ts:802)/재기동(`restoreTaskRegistryOnce`, :946)이 sqlite SoT 를 재적재해 삭제 태스크가 부활. FIND-002(P2, wrong-output): sqlite-direct reader `listFreshTasksForOwnerKey`(2092-2117)가 media-generation status 경로(`src/agents/media-generation-task-status-shared.ts`:119,314)에서 stale 값을 즉시 노출 — 같은 ownerKey 에 대해 in-memory 경로와 sqlite-direct 경로가 상반된 답을 반환. 결함의 본질은 sqlite 트랜잭션 부재가 아니라 in-memory↔sqlite 교차-스토어 경계 부재다(sqlite 측은 `withWriteTransaction` 으로 원자성 보장). pre-sol proof(`proofs/PROOF-CAND-047-pre-20260529-070740.md`, trials=2)에서 두 분기 모두 발산 직접 측정: divergenceCount=2, resurrectedCount=1.

it("does not diverge sqlite-direct reads when an upsert persist throws", () => {
  const ownerKey = "agent:main:main";
  const sqliteRow: TaskRecord = {
    ...createStoredTask(),
    taskId: "task-diverge",
    runId: "run-diverge",
    ownerKey,
    status: "running",
  };
  const sqliteState = new Map<string, TaskRecord>([[sqliteRow.taskId, sqliteRow]]);

  let failUpsert = false;
  const upsertTaskWithDeliveryState = vi.fn((params: { task: TaskRecord }) => {
    if (failUpsert) {
      throw new Error("SQLITE_FULL: database or disk is full");
    }
    sqliteState.set(params.task.taskId, params.task);
  });
  const deleteTaskWithDeliveryState = vi.fn((taskId: string) => {
    sqliteState.delete(taskId);
  });
  const listTasksForOwnerKey = vi.fn((key: string) =>
    [...sqliteState.values()].filter((t) => t.ownerKey === key),
  );

  configureTaskRegistryRuntime({
    store: {
      loadSnapshot: () => ({ tasks: new Map(sqliteState), deliveryStates: new Map() }),
      saveSnapshot: () => {},
      upsertTaskWithDeliveryState,
      deleteTaskWithDeliveryState,
      listTasksForOwnerKey,
    },
  });

  const initial = listFreshTasksForOwnerKey(ownerKey);
  expect(initial.find((t) => t.taskId === "task-diverge")?.status).toBe("running");

  failUpsert = true;
  expect(() =>
    markTaskTerminalById({ taskId: "task-diverge", status: "succeeded", endedAt: 200 }),
  ).toThrow(/SQLITE_FULL/);

  failUpsert = false;
  const after = listFreshTasksForOwnerKey(ownerKey);
  const seen = after.find((t) => t.taskId === "task-diverge");
  expect(seen?.status).toBe("running");

## 해결 후보

### 후보 0 — persist-before-in-memory (chosen)

- **요약**: `updateTask` / `deleteTaskRecordById` 에서 sqlite persist(`persistTaskUpsert` / `persistTaskDelete` + `persistTaskDeliveryStateDelete`) 를 in-memory Map mutate 보다 **먼저** 호출. persist 가 성공한 뒤에만 `tasks.set/delete` + 인덱스 갱신 + observer event emit 을 수행. persist throw 시 in-memory 는 전혀 손대지 않아 양 스토어가 일관 상태로 남는다.
- **change_scope**: S (1 production file + 1 test, ~60-100 line statement 재배치).
- **files_touched**:
  - `src/tasks/task-registry.ts` — `updateTask`(980-1011 영역: next/인덱스-diff 계산은 유지하되 persist 를 먼저, 그 후 `tasks.set`+인덱스 갱신), `deleteTaskRecordById`(2153-2173: persist 2건을 in-memory delete 앞으로).
  - `src/tasks/task-registry.store.test.ts` — 위 회귀 테스트.

### 후보 1 — rollback-on-persist-throw

- **요약**: in-memory 선커밋을 유지하되 persist 호출을 try/catch 로 감싸고, throw 시 catch 에서 in-memory 를 `current` 로 되돌린 뒤 re-throw.
- **change_scope**: S.
- **tradeoff**: 보상(rollback) 역연산이 두 함수에 분산되고 인덱스(owner/parentFlow/relatedSession/runId) 원복까지 정확히 역산해야 해 누락 위험이 크다. delete 는 삭제한 레코드+delivery-state+3개 인덱스 전부 재삽입 필요. 부분 성공(delete 성공 / delivery-state delete 실패) 시 복원 일관성도 까다롭다. persist-before 가 동일 효과를 더 단순히 달성하므로 비채택.

### 후보 2 — store-transaction-boundary

- **요약**: store 계약에 in-memory↔sqlite 를 묶는 상위 트랜잭션 helper(`withTaskRegistryWrite`) 도입, persist 성공 콜백 안에서만 in-memory commit.
- **change_scope**: M.
- **tradeoff**: store 인터페이스(`task-registry.store.types.ts`) + sqlite/test 구현 갱신 → M 규모, surface 확대, one-thing-per-PR 위반 위험. persist-before 가 in-file 재배치만으로 동등 효과를 내므로 과설계. 본 SOL scope 밖(별도 설계 제안 대상).

### 커밋 메시지 초안
```
fix(tasks): persist task store before in-memory mutation to prevent sqlite divergence

updateTask and deleteTaskRecordById commit the in-memory tasks /
taskDeliveryStates maps (and owner/parentFlow/relatedSession/runId
indexes) before calling the sqlite persist helpers, and neither persist
call is wrapped in a try/catch. The default store always binds the
transactional variants (upsertTaskWithDeliveryState /
deleteTaskWithDeliveryState), so persist always goes through
withWriteTransaction(BEGIN IMMEDIATE), which ROLLBACKs and re-throws on
SQLITE_BUSY (multi-writer busy_timeout exceeded), SQLITE_FULL (disk
full), or SQLITE_IOERR. The unhandled throw leaves the in-memory state
mutated while sqlite keeps the prior row, so the two stores diverge:
reload/restart resurrects deleted tasks (lost-delete), and the
sqlite-direct reader listFreshTasksForOwnerKey (used by
media-generation-task-status-shared) immediately returns stale rows that
contradict the in-memory path.

Persist to the store first and only mutate the in-memory maps and
indexes after persist succeeds. When persist throws, the in-memory state
is left untouched, keeping both stores consistent. Store contracts are
unchanged. Mirrors the persist-before-in-memory fix-shape of #83238.

AI-assisted: drafted with claude code (claude-opus-4-8).
```
