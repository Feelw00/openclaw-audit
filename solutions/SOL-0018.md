## 문제 요약

session-delivery 큐의 복구 경로 `drainQueuedEntry`(`src/infra/session-delivery-queue-recovery.ts:105-124`)는 entry 를 `await opts.deliver(entry)` 한 뒤 `await ackSessionDelivery(entry.id)` 로 큐 파일을 제거하는 at-least-once 큐다. deliver 가 성공(restart continuation 의 agentTurn 재실행 + 플랫폼 응답 전송 완료)했지만 ack 직전에 프로세스가 죽으면 큐 파일이 pending 으로 남고, 다음 복구가 그 entry 를 `deliver` 두 갈래(recovered/failed)로만 분류하며 무조건 재전달한다. deliver 결과는 "이미 전송됨" 과 "전송 전 transient 실패" 를 구분할 정보가 큐에 없어, 같은 사용자 턴이 두 번 실행되고(LLM/툴 등 비-idempotent side-effect) 응답이 중복 전송된다(wrong-output). 평행 outbound 큐는 정확히 이 시나리오를 `send_attempt_started`/`unknown_after_send` 마커 + `reconcileUnknownQueuedDelivery` + blind-replay 거부(`src/infra/outbound/delivery-queue-recovery.ts:418`)로 막지만, session 큐는 storage 타입(`QueuedSessionDelivery`, `session-delivery-queue-storage.ts:62`)에 `recoveryState` 필드 자체가 없어 동등 가드가 전무하다. pre-sol proof(`PROOF-CAND-050-pre-20260529-070811.md`)에서 deliverCount=2, deliveredIds 동일 uuid 2회, recoveryStateAfterCrash=field-absent 로 결함과 비대칭이 직접 측정됨.

## 재현 테스트

`openclaw/src/infra/session-delivery-queue.recovery.test.ts` 의 `describe("session-delivery queue recovery", ...)` 블록에 아래 `it(...)` 을 추가한다. 기존 테스트가 이미 `withTempDir` + `enqueueSessionDelivery` + `recoverPendingSessionDeliveries` + `deliver` 스텁(`vi.fn`) 패턴을 쓰므로 새 helper 가 필요 없다. profile 은 `infra`(`vitest.infra.config.ts`).

핵심: crash 를 별도 프로세스 없이 "deliver 성공 후 ack 1회 차단으로 unack pending 생성" 으로 모델한다. on-disk 결과(entry pending 잔존 + 마커 없음)가 production crash 와 byte-identical 이라 branch 충실(critical-devil caveat: 반드시 *재시작 경계 후 re-recover* 흐름이어야 in-memory dedupe 에 가려지지 않는다 — 이 테스트는 deliver fn 경계에서 두 번째 recover 를 직접 돌려 그 조건을 만족).

      },
      tempDir,
    );

    const deliver = vi.fn(async () => {
      deliverCount += 1;
    });
    const log = { info: vi.fn(), warn: vi.fn(), error: vi.fn() };

      .mockImplementationOnce(async () => {

    // PASS 2: 재시작 후 복구 재진입.
    await recoverPendingSessionDeliveries({ deliver, stateDir: tempDir, log });

    // 수정 전: deliverCount === 2 (blind replay → 턴 재실행 + 응답 중복 전송) → FAIL
    // 수정 후: deliverCount === 1 (recoveryState 마커 → reconciliation → blind replay 거부) → PASS

RED 기준(현재 코드): PASS 2 의 `drainQueuedEntry` 가 recoveryState 분기 없이 `deliver` 를 재호출 → `deliverCount === 2` → 단언 실패.
GREEN 기준(chosen_fix 후): PASS 1 의 deliver 직전/직후 `markSessionDeliveryPlatformSendAttemptStarted/OutcomeUnknown` 가 마커를 영속하고, PASS 2 의 `drainQueuedEntry` 가 그 마커를 보고 blind replay 를 거부(moveToFailed) → `deliver` 미재호출 → `deliverCount === 1`.

이식 후 검증: `pnpm test src/infra/session-delivery-queue.recovery.test.ts` (또는 `pnpm vitest -c vitest.infra.config.ts run session-delivery-queue.recovery`). 단, 위 테스트는 deliver fn 경계 모델이라 `deliverQueuedSessionDelivery` 내부의 실제 마커 호출까지는 검증하지 못함 — post-sol real-behavior-proof(아래)가 deliver→(no ack)→restart→re-recover 전 구간을 production 빌드로 측정해 보완한다.

## 해결 후보

### 후보 1 — mark-and-refuse-blind-replay (chosen)

- **요약**: outbound 와 동형의 마커를 session 큐에 이식한다.
  1. `QueuedSessionDelivery`(storage.ts:62)에 `platformSendStartedAt?: number` + `recoveryState?: "send_attempt_started" | "unknown_after_send"` 추가.
  2. storage 에 `markSessionDeliveryPlatformSendAttemptStarted(id)` + `markSessionDeliveryPlatformOutcomeUnknown(id)` 추가(outbound `deliver.ts:600,618` 의 `markDelivery*` 와 동형, 마커만 영속).
  3. `deliverQueuedSessionDelivery`(server-restart-sentinel.ts:253-396)의 플랫폼 전송(`sendDurableMessageBatch`, :355) 직전에 `markStarted`, 결과 분기 직후(전송 성공/실패 불명 구간)에 `markUnknown` 을 영속.
  4. `drainQueuedEntry`(recovery.ts:105-124)에 outbound `delivery-queue-recovery.ts:371-442` 와 같은 pre-deliver 분기: `recoveryState === "send_attempt_started" | "unknown_after_send"` 면 adapter reconcile 없이 blind replay 를 거부하고 `moveSessionDeliveryToFailed` 로 fail-safe(deliver 재호출 안 함).
- **change_scope**: S (~50-130 line, 3 src file + 1 test).
- **files_touched**: `session-delivery-queue-storage.ts`, `session-delivery-queue-recovery.ts`, `server-restart-sentinel.ts`, (test) `session-delivery-queue.recovery.test.ts`.
- **tradeoff**:
  - 장점: adapter reconcile 능력 없이도 중복 실행/중복 전송을 0 으로 만든다(fail-safe — 의심되면 재전달 안 함). outbound 가 adapter capability 부재 시 정확히 같은 `:418 refusing blind replay` 경로로 fail-safe 하므로 두 큐의 정책이 통일된다. one-thing-per-PR 부합, dep 추가 없음.
  - 단점: "이미 전송됐지만 crash" 와 "전송 직전 crash" 를 구분 못 해, 진짜 전송 전에 죽은 entry 도 replay 되지 않고 failed/ 로 간다 — at-least-once 보장이 그 좁은 window 에서 약화. 그러나 wrong-output(중복 전송/턴 재실행) 회피가 우선이고, 이 trade-off 는 outbound 가 이미 채택한 동일 fail-safe 다.

### 후보 2 — full-adapter-reconcile

- **요약**: 후보 1 위에 outbound `reconcileUnknownQueuedDelivery`(recovery.ts:153-194) 와 동형의 adapter 질의를 session deliver 경로에 추가. `recoveryState` 가 unknown 이면 채널 adapter 의 `reconcileUnknownSend` capability 에 "이 messageId 가 이미 전송됐는가" 를 물어 sent → ack(replay 안 함) / not_sent → 안전 replay 로 분기.
- **change_scope**: M.
- **tradeoff**: 정확도 최고(전송됐으면 ack, 안 됐으면 replay 로 at-least-once 도 유지). 그러나 session deliver 는 `dispatchAssembledChannelTurn` → 채널 adapter 까지 닿아 adapter 마다 `durableFinal.reconcileUnknownSend` 구현/배선이 필요 → 다수 adapter 영향, M PR. 단일 PR scope 초과 위험. 후보 1 머지 후 별도 follow-up 으로 격상 가능.

### 후보 3 — persisted-processed-messageid-dedup

- **요약**: restart continuation 의 stable messageId 를 turn 재실행 직전 영속 처리 마커로 기록하고, 재진입 시 그 messageId 가 이미 처리됐으면 deliver skip + ack. critical-devil 가 cross-restart 를 못 막는다고 확인한 in-memory `claimInboundDedupe` 의 영속판.
- **change_scope**: S.
- **tradeoff**: 마커 박는 시점("처리 시작" vs "전송 완료")에 따라 같은 crash window 가 재발할 수 있고(전송 완료 후 마커 영속 전 crash → 여전히 blind replay), outbound 큐와 메커니즘이 갈려 "두 큐 정책 통일" warrant 와 어긋난다. 메인테이너 설득력에서 outbound 패턴 재사용(후보 1)이 우위.

```
fix(infra): reconcile unacked session deliveries to prevent duplicate replay on restart

The session-delivery recovery path drainQueuedEntry
(src/infra/session-delivery-queue-recovery.ts:105-124) delivers an entry
then acks it (at-least-once). If a restart-continuation agentTurn delivery
succeeds (turn re-run + platform send via dispatchAssembledChannelTurn /
sendDurableMessageBatch) but the process is killed before ackSessionDelivery,
the queue file stays pending and the next recovery blindly re-delivers it:
deliver is classified into only recovered/failed, with no marker recording
whether the platform send already happened. The same user turn runs twice
(non-idempotent LLM/tool side-effects) and the reply is sent twice.

The parallel outbound queue already guards exactly this: it persists
send_attempt_started / unknown_after_send markers
(src/infra/outbound/deliver.ts:600,618) and on recovery refuses a blind
replay for those states without adapter reconciliation
(src/infra/outbound/delivery-queue-recovery.ts:418). The session queue's
QueuedSessionDelivery type has no recoveryState field at all
(session-delivery-queue-storage.ts:62), so the two queues' guarantees diverge.

Port the outbound marker pattern to the session queue: add
platformSendStartedAt / recoveryState to QueuedSessionDelivery, persist the
markers around the platform send in deliverQueuedSessionDelivery, and make
drainQueuedEntry refuse a blind replay (move-to-failed, fail-safe) when an
entry is recovered in send_attempt_started / unknown_after_send.

AI-assisted: drafted with claude code (claude-opus-4-8).
```
