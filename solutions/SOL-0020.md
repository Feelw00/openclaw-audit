# SOL-0020 — session-delivery drain: 기존 SQLite recovery_state 컬럼 배선으로 blind replay 차단

## 문제 (CAND-056, 현재 upstream 재확인)

session-delivery 복구 경로 `drainQueuedEntry`(session-delivery-queue-recovery.ts:111)가 entry 를
`await deliver(entry)` 한 뒤 `ackSessionDelivery`(:121)로 제거한다(at-least-once). deliver 성공
(agentTurn 재실행 + 플랫폼 응답 전송) 직후 ack 직전 crash 시 entry 가 pending 으로 남고, 다음 복구
(recoverPendingSessionDeliveries:214)가 reconciliation 없이 동일 entry 를 재-deliver → 턴 중복 실행 +
응답 중복 전송.

#88665("move delivery queues to SQLite")는 이 recovery 모듈을 건드리지 않았다. pre-sol proof 가
현재 upstream(SQLite backing) 에서 deliverCount=2 로 결함 생존을 실측 확인했다.

## 선택한 fix (chosen_fix=0): wire-recovery-state-into-session-drain

#88665 가 공용 backing(delivery-queue-sqlite.ts)에 `recovery_state` 컬럼을 이미 추가했으나
세션 큐는 미사용이다. 이 fix 는 그 컬럼을 세션 drain 에 배선한다:

1. `session-delivery-queue-storage.ts`: `QueuedSessionDelivery` 에 `recoveryState` 노출 +
   `markSessionDeliveryPlatformSendAttemptStarted` / `markSessionDeliveryPlatformOutcomeUnknown` /
   `clearSessionDeliveryRecoveryState` 를 `updateDeliveryQueueEntry` 로 구현(upsert 가 `recovery_state`
   영속 — delivery-queue-sqlite.ts:118 로 feasibility 확인).
2. `session-delivery-queue-recovery.ts` `drainQueuedEntry`: deliver 직전 `send_attempt_started`,
   반환 후 `unknown_after_send` 영속; 복구 재진입 시 그 상태면 blind replay 거부 + `moveToFailed`
   (fail-safe). `delivered` 플래그로 deliver 반환 후 marker/ack 실패도 refuse, pre-send throw 만
   clear+retry.

**sentinel.ts 미변경**: #88665 가 restart continuation 의 실제 송신을 outbound 큐
(enqueueDelivery/ackDelivery, 자체 recovery_state 가드 보유)로 이관했다. 따라서 SOL-0018 의 3라운드
리뷰를 유발한 "sentinel inline-send 가 partial_failed 후 throw" 하는 sent-before-error 클래스가 본
아키텍처에서는 발생하지 않는다. 마커는 `drainQueuedEntry` 의 deliver seam 만 감싸면 충분하며,
SOL-0018 의 typed-error(SessionDeliverySendUncertainError) 메커니즘은 thrower 가 사라져 불필요(dead).

## 근거 (외부)

- clawsweeper(#88015 2026-05-29 코멘트): "marker-and-refuse path is the narrow maintainable fix
  because it matches the existing outbound queue's `unknown_after_send` recovery contract."
- 설계문서 `docs/concepts/message-lifecycle-refactor.md:443`: platform success 후 receipt commit 전
  attempt 는 `unknown_after_send` 로 resume 해야 하며 blind replay 금지(중복 visible 메시지가 명시
  공시된 tradeoff 가 아닌 한).

## tradeoff / 미해결

- fail-safe refuse 는 adapter reconcile 없이 중복을 0 으로 만들되, 진짜 pre-send crash 도 좁은 window
  에서 failed/ 로 갈 수 있어 at-least-once 가 약화(outbound 큐와 동일 선택). 정확 reconcile(adapter
  capability)은 full-adapter-reconcile 후보(M)로 분리.
- abhinas90(커뮤니티) 코멘트의 seq/cursor·idempotency-key 제안은 receiver-side-sequence-or-turn-idempotency
  후보로 reject(위 fix_approach_candidates 참조): idempotencyKey 는 이미 enqueue-only 로 이 window 미커버,
  seq/cursor 는 다른 축의 M+ 변경.
