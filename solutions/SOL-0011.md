## 문제 요약

`src/gateway/server/ws-connection.ts:354-424` 의 WS connection close 핸들러는
session-event 구독 해지 / nodeRegistry unregister / presence 갱신 / node-wake
state 정리만 수행. `chatAbortControllers` 의 `ownerConnId === connId` 매칭
entry 는 abort 하지 않는다.

`registerChatAbortController` (`src/gateway/chat-abort.ts:73-115`) 는 entry 의
`ownerConnId` 필드에 chat.send / agent.request 시점의 owner WS connId 를
저장한다. 이 필드는 abort RPC 권한 판정 (`canRequesterAbortChatRun`) 의
한정된 5개 호출 (chat.ts:1570/1571/1577/2196, agent.ts:1330) 에서만
소비된다 — disconnect 시 자동 abort 경로는 부재.

발현 sequence:
1. user (operator/webchat/cli/mobile-node) 가 chat.send / agent.request 발행
   → `registerChatAbortController` 가 AbortController + entry 등록
   (`ownerConnId: connId`).
2. runner 가 LLM 호출, tool 실행, 외부 API call 시작 (수 초~수 분).
3. user 가 네트워크 단절 / 탭 종료 / Ctrl-C / 모바일 backgrounding 으로
   WS close.
4. close 핸들러는 chatAbortControllers 미터치 → `entry.controller.signal.aborted=false`.
5. runner 는 abort signal 못 받음. LLM 호출 / tool 실행 / 외부 API call
   끝까지 진행. broadcast 결과는 닫힌 socket 으로 send → swallow.
6. `expiresAtMs` (minMs=2분 floor + graceMs=60s, timeoutMs 가 더 크면 그
   값) 후 maintenance interval (`server-maintenance.ts:153-174`) 의 sweep
   이 timeout 으로 abort. 정상 운영에서는 5-30분 늦은 cleanup.

영향:
- LLM 토큰 과금 누적 — user 가 결과 수신 불가한데도 결제.
- tool 실행 부작용 — file write / MCP / shell exec / 외부 메신저 메시지
  발사. user intent 와 분리된 시점에 외부 상태 변경.
- 동일 user 의 다음 chat.send 가 maintenance sweep 전이라면 같은 sessionKey
  의 이전 run 이 여전히 활성 상태로 잡혀 broadcast / accounting 오염.

`PROOF-CAND-038-pre-20260515-085213.md` 의 production-faithful e2e 측정에서
`chain_works_trials=1, abort_observed_trials=0, mock_request_started_count=1,
mock_hold_started_count=1, mock_client_disconnected=[]` — chain 이 LLM 까지
도달했고 ws.close 후에도 mock `req.on("close")` 이 미 fire (LLM 호출이
계속 hold) 직접 측정.

### 커밋 메시지 초안
```
fix(gateway): abort chat runs owned by disconnecting WS connection

The WS connection close handler (ws-connection.ts) cleans up session-event
subscriptions, node registry entries, presence, and node-wake state, but
never iterates chatAbortControllers to abort runs whose ownerConnId
matches the closing connId. registerChatAbortController stores ownerConnId
specifically for abort-authorization checks (canRequesterAbortChatRun), but
nothing else consumes it on disconnect — so an in-flight chat.send /
agent.request keeps invoking the LLM, running tools, and emitting
broadcasts into a closed socket until the maintenance sweep
(expiresAtMs, minMs=2min) times it out. End users pay tokens and tools
mutate external state long after they intended to cancel.

Iterate chatAbortControllers on close and call abortChatRunById for each
entry where ownerConnId === connId. abortChatRunById already handles
idempotency, broadcast, removeChatRun, and cancelled lifecycle events;
GatewayRequestContext already exposes the full ChatAbortOps surface, so
no plumbing is required.

AI-assisted: drafted with claude code (claude-opus-4-7).
```
