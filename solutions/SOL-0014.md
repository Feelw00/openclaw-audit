## 문제 요약

`src/agents/sessions/auth-storage.ts` 의 `FileAuthStorageBackend.withLock`(sync, line 119)
과 `withLockAsync`(async, line 164) 가 `auth.json` 갱신을 raw `writeFileSync(this.authPath, next)`
+ `chmodSync` 로 처리한다. 이는 대상 경로를 OS 레벨에서 `O_TRUNC` 로 직접 열어 기존 내용을 0 으로
만든 뒤 새 바이트를 기록하는 in-place 재기록이라, truncate 와 마지막 바이트 flush 사이가 비원자다.
그 창에서 SIGKILL / 전원차단 / 패닉 시 `auth.json` 은 0바이트 또는 부분 JSON 으로 디스크에 잔존한다.

`auth.json` 은 API 키와 OAuth refresh 토큰의 유일한 영속 SoT(재생성 불가). 손상 시 다음 기동
`reload()` 의 `parseStorageData` → `JSON.parse(부분문자열)` 이 throw → `loadError` 세팅, `this.data = {}`.
이후 `persistProviderChange()` 가 `if (this.loadError) return;`(line 287) 로 손상 파일을 새 값으로
덮어쓰지도 못해 — 사용자가 명시적으로 `/login` 재인증하기 전까지 전 provider 자격증명 lockout, LLM
호출 전면 불가. OAuth refresh(line 164) 가 만료 주기마다 동일 write 를 수행해 노출이 반복적이다.
proper-lockfile advisory lock(115)은 프로세스 간 mutual-exclusion 만 제공하고 단일 write 의
crash-atomicity 와는 무관하다 (lock 보유 중 crash 하면 파일은 이미 truncated).

동일 코드베이스의 `src/agents/session-file-repair.ts:409` `repairSessionFile()` 은 동일 종류의
in-place 전량 재기록을 `replaceFileAtomic`(temp 작성 후 atomic rename) 으로 처리한다. atomic 헬퍼가
트리 안에 존재하고 실제로 쓰이는데 더 critical 한 자격증명 writer 만 raw write 라 atomic 규율이 불균일하다.

pre-sol proof(`PROOF-CAND-045-pre-20260529-070725.md`, scenario `proof-CAND-045`, trials=2)에서
crash-truncate 분기가 `loadFailed=true / keyAfterCrash=<empty> / recoveryNoOp=true / lockout=true`,
control 분기는 정상(`lockout=false`)으로 결함이 재현됨.

> scope 주의(cross-review 합의): CAND-045 epic 은 auth.json(FIND-001) / 세션 transcript(FIND-002)
> / settings.json(FIND-003) 세 writer 를 묶지만, 본 SOL 은 scope-down 합의에 따라 FIND-001 단건만
> 다룬다. FIND-002(transcript full-overwrite migrate) 는 별도 후속 SOL, FIND-003(settings, graceful
> `{}` fallback 이라 lockout 없음 → 최약) 은 후순위/제외.

- **RED (수정 전, raw `writeFileSync`)**: crash 가 실제 `auth.json` 경로를 truncate → 다음 기동
  `reload()` 의 `JSON.parse` throw → `loadError` → `getApiKey` 가 `undefined` → seed 자격증명 lockout.
  `reopened.drainErrors()` 가 비어있지 않거나 `getApiKey` 가 seed 값을 반환하지 못해 실패.
- **GREEN (수정 후, `replaceFileAtomicSync`)**: write 는 `.tmp` temp 파일(flag `"wx"`)로 향하고
  crash 가 거기서 발생 → atomic rename 미실행 → 원본 `auth.json` 이 seed 값을 그대로 보존. reopen 시
  drainErrors 0, `getApiKey("anthropic") === "sk-test-SEED-12345"`.

## 해결 후보

### 후보 1 — replace-raw-writefilesync-with-atomic-sync (chosen, XS)

withLock(119-120) / withLockAsync(163-165) 의 `writeFileSync(this.authPath, next, "utf-8")` +
`chmodSync(this.authPath, 0o600)` 두 줄을 다음 한 호출로 교체:

```ts
import { replaceFileAtomicSync } from "../../infra/replace-file.js";
// ...
if (next !== undefined) {
  replaceFileAtomicSync({
    filePath: this.authPath,
    content: next,
    mode: 0o600,
    tempPrefix: "auth.json",
  });
}
```

`replaceFileAtomicSync`(`@openclaw/fs-safe/atomic`, `src/infra/replace-file.ts:13` 재노출)는
temp 파일(`flag: "wx"`)에 content 를 쓰고 `mode` 로 0o600 을 부여한 뒤 `renameSync` 로 atomic 교체한다.
crash 가 temp write 중 발생하면 원본 `auth.json` 은 전혀 건드려지지 않아 자격증명이 보존된다.
`mode: 0o600` 이 별도 `chmodSync` 를 대체하므로 동일 보안 모드를 유지한다.

- **change_scope**: XS (`auth-storage.ts` 두 write 지점 + import 1줄, ~10줄. test 신규).
- **files_touched**: `src/agents/sessions/auth-storage.ts`(119-120, 163-165, import),
  `src/agents/sessions/auth-storage.test.ts`(신규).
- **tradeoff**: 동일 트리에서 이미 쓰이는(session-file-repair.ts:409) 헬퍼 재사용 — 신규 dep/아키텍처
  변경 없음. withLock(sync)/withLockAsync(async) 둘 다 sync 변형 하나로 통일(I/O 가 sync 라도 호출부
  계약 영향 없음 — async 함수 안에서 sync write 호출은 정상). `ensureFileExists`(77)의 초기 `"{}"` seed
  write 는 빈 파일이라 손상돼도 lockout 아님 → 함께 atomic 화 필수는 아님(원하면 추가 가능하나 scope
  최소화 위해 제외). proper-lockfile advisory lock 과 rename 상호작용: lock 파일은 원본 경로 기준 별도
  디렉터리라 rename 무관(검토 완료).

### 후보 2 — write-temp-then-rename-inline (S, 비권장)

replaceFileAtomicSync 를 안 쓰고 auth-storage 안에서 temp write + renameSync + chmodSync 를 직접
인라인. 동일 트리에 검증된 헬퍼가 있는데 중복 재구현(temp prefix / cleanup / rename-retry /
copy-fallback / EXIT 정리 등 헬퍼가 이미 다루는 엣지를 다시 짜야 함) → 리뷰/유지보수 부담만 늘고

### 커밋 메시지 초안
```
fix(agents): atomic auth.json write to prevent credential lockout on crash

FileAuthStorageBackend.withLock / withLockAsync persist auth.json (the
sole source of truth for API keys and OAuth refresh tokens) with a raw
writeFileSync, which O_TRUNC-opens the destination in place. If the
process is SIGKILLed or the machine loses power between the truncate and
the final flush, auth.json is left empty or partially written. On the
next boot reload()'s JSON.parse throws, loadError is set, and
persistProviderChange() early-returns on loadError so the corrupt file is
never overwritten -- every provider credential is locked out until the
user re-authenticates with /login. OAuth refresh performs the same write
on every token expiry, so the exposure recurs.

Replace both raw writeFileSync calls with replaceFileAtomicSync (already
used in this tree by session-file-repair.ts for the same kind of in-place
rewrite), which writes to a temp file and atomically renames it into
place. A crash now hits the temp file and leaves auth.json intact. The
mode option preserves the 0o600 permission, removing the separate
chmodSync.

AI-assisted: drafted with claude code (claude-opus-4-8).
```
