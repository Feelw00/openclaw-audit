## Problem

manual cron runs that exceed `TASK_RECONCILE_GRACE_MS` (5 min, `task-registry.maintenance.ts:61`) surface a transient `lost` task-registry status and a `Background task lost` system message **before** `resolveDurableCronTaskRecovery` (1fae716a04, merged 2026-04-26) reconciles. The final state is correct, but the user who triggered the run sees an inaccurate intermediate state.

## Why this is narrower than SOL-0007

- **Startup catchup path 제외**: 새 main 의 `cron.start()` 가 `runMissedJobs(state, { deferAgentTurnJobs: true })` (`ops.ts:171-174`) 로 호출하여 agentTurn 은 startup 즉시 path 에서 제외. non-agentTurn payload 의 5-10분 실행은 거의 이론적 (hot-path-tracer 평가 score 1-2). 추가로 clawsweeper Codex P2 결함 (multi-candidate clear timing) 까지 안고 있음. 메인테이너 axis (1fae716a04) 와 직접 중복.
- **Manual run path 만 유지**: 사용자가 `openclaw cron run <id> --force` 로 트리거 시 `agentTurn` payload 도 그대로 실행 — `AGENT_TURN_SAFETY_TIMEOUT_MS = 60min` (force 모드) 또는 default 10min timeout 까지 합법. 5분+ 실행 빈도 hot-path-tracer 평가 high. 메인테이너 axis 와 충돌 없는 깨끗한 빈틈.

## Mechanism

- `task-registry.maintenance.ts` 의 `hasBackingSession` 의 cron 분기 (`isCronRuntimeAuthoritative()=true` production 기본값) 는 오직 `isCronJobActive(jobId)` 단독 의존.
- `prepareManualRun` (`ops.ts:654`) 와 `finishPreparedManualRun` (`ops.ts:702`) 는 `tryCreateManualTaskRun` 으로 task 를 만들지만 `markCronJobActive` 호출 없음. 즉 cron task 는 ledger 에 running 으로 등록되지만 backing-session 신호가 없어 sweeper grace (5분) 후 'lost' 마킹.
- 이후 job 종료 시 `applyJobResult` 가 `lastRunStatus` / `lastRunAtMs` 갱신 → `resolveCronJobStateRecovery` 가 다음 maintenance tick 에서 'finished' 로 정정.
- 우리 fix 는 그 grace window 자체를 차단 (mark/clear pair 로 `isCronJobActive=true` 보장).
