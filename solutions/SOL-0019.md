## 문제 요약

같은 stuck-session 복구를 두 모듈이 각자의 in-flight Set 으로 추적하는데 키 입도가 다르다.
coordinator 의 `recoveryRequestKey` (diagnostic-session-recovery-coordinator.ts:63-69) 는
`${ref}:${request.stateGeneration ?? "unknown"}` 를, runtime 의 `recoveryKey`
(diagnostic-stuck-session-recovery.runtime.ts:55-57) 는 `params.sessionKey?.trim() ||
params.sessionId?.trim()` (ref only) 만 쓴다.

heartbeat (diagnostic.ts:1268/1291, 30초 주기) 가 같은 세션을 stuck 으로 반복 판정하는데,
첫 tick 의 `recover()` 가 dynamic import + abort/drain await (settleMs <= 15s) 로 in-flight 인
동안 generation 이 bump 되면 — coordinator 키는 `S:G -> S:G+1` 로 바뀌어 dedup 을 통과해
두 번째 `session.recovery.requested` 이벤트를 발행하고 `recover()` 를 재호출하지만, runtime 은
같은 ref `S` 라 `already_in_flight` 로 skip 한다. 결과는 (1) 중복 requested 이벤트로 복구 시도
횟수/latency 메트릭 부풀림, (2) `session.recovery.requested` 와 `completed` 의 1:1 불일치,
(3) coordinator 와 runtime 두 dedup 계층의 in-flight 뷰 어긋남이다. `skipped` outcome 은
`recoveryOutcomeMutatesSessionState=false` (diagnostic-session-recovery.ts:88-93) 라 state
를 mutate 하지 않으므로 데이터 손상은 아니고 영향은 관측/신뢰성에 한정 → P2.

발현 분기는 cross-review 합의대로 **idle-queued-recoverable-stall** (diagnostic.ts:1247,
`isIdleQueuedRecoverableSessionStall` :542-563) 단일 분기로 한정된다. processing 분기
(:1253, `ageMs = now - state.lastActivity > stuckSessionWarnMs`) 는 generation mutator 3종
(logMessageQueued :657 / logSessionStateChange :869 / markDiagnosticSessionProgress :915) 이
모두 `state.lastActivity = Date.now()` 를 동시에 수행해 다음 tick 재판정이 자기상쇄된다
(CAL-001 형 co-located unconditional guard). 반면 idle-queued-stall 분기는
`activity.lastProgressAgeMs` (diagnostic-run-activity.ts:319, 별도 store) 를 키로 쓰고
`logMessageQueued` 는 `touchSessionActivity` (tool/model/run 이벤트에서만 발화) 를 거치지 않아
lastProgressAgeMs 를 갱신하지 않으므로, 큐 메시지가 generation 만 +1 하고 stall 판정은 유지된다.

pre-sol proof (`PROOF-CAND-053-pre-20260529-070828.md`, scenario `proof-CAND-053`, trials=2,
status collected) 가 production-faithful 빌드로 비대칭을 직접 측정: `coordinatorDuplicateOnBump=2`
(generation bump 시 requested 2회, generations [0,1]), `coordinatorDedupNoBump=1` (bump 없으면
1회), `runtimeRefDedup=true` (T1 aborted, T2 skipped/already_in_flight) → `asymmetryReproduced=true`.

```ts
    // idle-queued-recoverable-stall 셋업: embedded run 소유권 + idle + 큐 적재.
    logSessionStateChange({ sessionId: "s1", sessionKey: "main", state: "processing" });
    markDiagnosticEmbeddedRunStarted({ sessionId: "s1", sessionKey: "main" });
    logSessionStateChange({ sessionId: "s1", sessionKey: "main", state: "idle" });

    // T1 tick: lastProgressAgeMs > staleMs → recoveryEligible → coordinator 키 S:G add,
    // requested #1 발행, recover() in-flight (pending) 시작.
    vi.advanceTimersByTime(59_000);
    logMessageQueued({ sessionId: "s1", sessionKey: "main", source: "t1" });
    vi.advanceTimersByTime(1_000);
    await Promise.resolve();
    expect(recoverStuckSession).toHaveBeenCalledTimes(1);

    // in-flight 윈도우 중 새 메시지 큐잉 → state.generation +1 (단 lastProgressAt 미갱신).
    // 다음 tick 에서 coordinator 키가 S:G+1 로 바뀐다.
    logMessageQueued({ sessionId: "s1", sessionKey: "main", source: "t2-followup" });

    // T2 tick (30s 후): 같은 세션이 여전히 idle-queued-stall → 재판정.
    vi.advanceTimersByTime(30_000);
    await Promise.resolve();
  } finally {
    resolveRecovery?.({
      status: "skipped",
      action: "observe_only",
      reason: "already_in_flight",
      sessionId: "s1",
      sessionKey: "main",
    });
    await Promise.resolve();
    unsubscribe();
  }

  const requestedEvents = events.filter(
    (event) => event.type === "session.recovery.requested",
  );
  // 수정 전(RED): coordinator 키 = `${ref}:${generation}` 라 S:G 와 S:G+1 이 별개 →
  //   두 번째 requested 이벤트가 발행되어 requestedEvents.length === 2.
  //   runtime 은 ref 동일이라 실제 복구는 already_in_flight 로 skip — 중복 이벤트만 남는다.
  // 수정 후(GREEN): coordinator 키를 ref-only 로 정렬 → S:G+1 이 in-flight S 와 충돌 →
  //   coordinator 도 already_in_flight 로 흡수 → requestedEvents.length === 1
  //   (두 dedup 계층 입도 일치).
  expect(requestedEvents).toHaveLength(1);
});
```

### 커밋 메시지 초안
```
fix(logging): align diagnostic recovery in-flight dedup keys

The stuck-session recovery coordinator and runtime track in-flight
recoveries with different key granularities. The coordinator's
recoveryRequestKey is `${ref}:${stateGeneration ?? "unknown"}` while
the runtime's recoveryKey is ref-only (sessionKey || sessionId). The
30s heartbeat re-classifies the same stuck session across ticks; while
the first recover() is still in-flight (dynamic import + abort/drain
await, settleMs up to 15s), a queued message bumps state.generation.
The coordinator key then becomes `S:G+1`, passes its dedup, and emits a
second session.recovery.requested event plus a re-entrant recover()
call -- but the runtime sees the same ref `S` and returns
already_in_flight, so no recovery actually runs. The duplicate
requested event inflates recovery-attempt/latency metrics and breaks the
requested/completed 1:1 invariant; the two dedup layers' in-flight views
diverge. skipped outcomes are non-mutating so no state corruption.

Align the coordinator's in-flight dedup key to ref-only, matching the
runtime. Staleness is still validated separately via stateGeneration in
applyRecoveryOutcomeToDiagnosticState and the runtime's stale check, so
this only collapses duplicate in-flight requests for the same logical
session. Regression test added under the idle-queued-stall branch.

AI-assisted: drafted with claude code (claude-opus-4-8).
```
