## 문제 요약

`src/gateway/server-runtime-services.ts:156-190` 의 두 recovery 함수가
cancellation handle 도 isClosing 가드도 갖지 않아 boot 직후 SIGTERM 시
tearing-down state 에서 background work 가 계속 fire:

- `recoverPendingOutboundDeliveries` (L156-170): 즉시 fire-and-forget async
  IIFE. 동적 `await import("../infra/outbound/delivery-queue.js")` →
  `recoverPendingDeliveries(deliver=deliverOutboundPayloadsInternal, ...)`.
  handle 미반환. caller 가 close 시 abort 통로 부재.
- `recoverPendingSessionDeliveries` (L172-190): `setTimeout(callback, 1250)`.
  `timer.unref?.()` 만 호출. handle 미반환. `timer.unref()` 는 event-loop alive
  카운터에서 timer 제외만 — queued callback 자체는 process 가 다른 작업으로
  살아있는 동안 fire (close prelude 가 다른 비동기 작업으로 process alive).

caller (`server.impl.ts:1430-1453` `activateScheduledServicesWhenReady`) 는
`closePreludeStarted` 로 activate 진입만 보호. activate 후 background work
의 cancellation 통로 없음. `activateGatewayScheduledServices` 의 return
타입 (server-runtime-services.ts:255-258 `{heartbeatRunner,
stopModelPricingRefresh}`) 에 recovery stop handle 부재.

발현 sequence (PROOF-CAND-039 5/5 trial):
1. `[gateway] ready` 직후 1250ms 이내에 SIGTERM.
2. recovery IIFE (또는 setTimeout fire) 가 dynamic import 시작.
3. close prelude 가 동시 진행 — channelManager / cron / sidecars dispose.
4. recovery 가 `deliverOutboundPayloadsInternal` 호출 → 이미 dispose 된
   channelManager / pending state 에 접근:
   - error log noise (`Delivery recovery failed: ...`).
   - 외부 채널 (Slack/Telegram/SMS) 에 의도치 않은 메시지 발사 (recovery 가
     pending entry 를 fire 처리).
   - partial state 디스크 잔존 (entry 가 in-flight 인 채 process exit).
5. close prelude 가 in-flight recovery 의 background promise 를 기다리며
   shutdown 지연 (PROOF 의 `close_prelude_ms=2.3s` 패턴).

같은 파일 `scheduleGatewayPostReadyMaintenance` (L103-154) 가 같은 startup
window 의 다른 background work 에 대해 `isClosing()` 가드 +
`clearGatewayMaintenanceHandles` 패턴을 보유. 비대칭 누락 — 본 SOL 은 그
패턴을 두 recovery 함수에 forward-apply.

stopStartupRecovery callback, and have server.impl.ts wire
closePreludeStarted into both the predicate and the close path.
